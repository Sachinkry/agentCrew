3. ARCHITECTURE
=====================================================================
Four agents plus deterministic services.

AGENTS (each = system prompt + tool set + zod output schema, plain TS functions, no agent framework):
1. OPERATOR — owns the goal. Each simulated day: read metrics, ask Analytics for a diagnosis, choose 1-2 actions, delegate tasks, start/close experiments. The ONLY agent that changes strategy. Must cite the metric it read for every action (logged to events).
2. CONTENT — builds products and writes everything public: product artifacts, listings, landing pages, X posts, email copy. Must pass verify_claims before publishing a listing.
3. ANALYTICS & MARKET — demand research, funnel analysis by channel (views -> cart -> purchase), experiment readouts, ranked build/retire list.
4. SUPPORT — pre-sale questions, delivery issues, refund/complaint handling. Proposes refunds; policy engine decides.

SERVICES (code, not agents; available to agents as tools, or Operator-only where noted):
- verify.ts: verify_claims(product_id) — runs artifact checks (tests pass / formulas recalc with zero errors / each listing claim matches artifact facts); returns per-claim pass/fail. Listing may only use verified claims.
- policy.ts: policy.check(action) on EVERY write tool. Rules: price floor = min margin %, max discount %, refund auto-approve limit (above -> approval queue), daily spend cap (inference + other), per-order inference cost cap, posts require approval. Log every block to events and run_metrics.policy_blocks.
- metrics.ts: read-only views over ledger: revenue, COGS, inference cost, platform fees, profit, conversion by channel, cost per order.
- ledger.ts: append-only money log. Every LLM call writes an inference entry automatically (core/llm.ts). Profit = SUM(ledger). Never store profit as a mutable field.
- approvals.ts: queue for posts / large refunds. In demo mode, auto-approve via a CLI flag but still log.
- sim/: seeded clock, buyer personas, traffic per channel, purchase-probability model, failure injection.
- trace.ts: neatlogs wrapper around every agent step and tool call.

DAILY LOOP (one simulated day):
1. Sim generates traffic per channel (web, x) and tickets.
2. Support handles tickets.
3. Operator tick: read yesterday's metrics -> ask Analytics for diagnosis -> choose actions.
4. Analytics returns funnel leaks by channel, significant experiment results, ranked build/retire list.
5. Operator creates tasks for Content (new listing, page rewrite, post batch, new product) and starts/closes experiments.
6. Content executes, passes verify_claims, publishes; posts go to approval queue.
7. Day closes; write run_metrics.

OPERATOR RULES (enforced in code):
- One active experiment per (lever, product).
- Minimum sample (default 200 sessions) before score_experiment treats a result as significant.
- Auto-revert an experiment if profit per order goes below zero.
- Max N actions per tick.

12. DEMO FAILURES -> FIXES (each needs: baseline run showing bug, fix, Entire checkpoint, fixed run, metric delta)
=====================================================================
F1. Content publishes an unverified claim (e.g. "includes 500 rows" when file has 312). Baseline: verify gate disabled. Fix: verify_claims required before publish; Listing receives verified claims only. Metric: claim_verified_rate -> 100%.
F2. Operator applies a discount that drives margin negative. Fix: policy.check price floor + auto-revert rule. Metric: policy_blocks logged, profit recovers.
F3. Operator rotates budget/focus to a channel based on thin data. Fix: minimum-sample rule in score_experiment. Metric: fewer reverted experiments.
F4. Support over-refunds / ignores policy. Fix: Support only proposes; policy engine decides; large refunds -> approvals. Metric: refund_policy_violations -> 0.
Compare via same seed, same days, baseline.json vs fixed.json. Output a markdown table: claim_verified_rate, policy_blocks, cost_per_order, profit, conversion by channel.
